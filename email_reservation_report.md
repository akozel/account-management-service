# Email reservation: review и состояние исправлений

## Обновление после реализации верификации — 13 сентября 2026

Исправлен обход канонического ключа email: парсер отклоняет display names, обёртки `<…>`, quoted local parts и domain literals; `parse`, `FromStr` и `Deserialize` используют одну нормализацию. Пробелы по краям удаляются, адрес приводится к нижнему регистру. Особенности конкретных провайдеров (`+tag`, точки) не объединяются. Уже сохранённые некорректные ключи автоматически не мигрируются.

При резервировании генерируется семизначный код, который хранится в событии и восстанавливается в агрегате. Добавлены `POST /email-verifications/{email}/request-new-code` для выдачи нового кода и `GET /email-verifications/{email}/confirm?code=1234567` для подтверждения. Подтверждение проверяет и состояние `VerificationInProgress`, и совпадение с текущим кодом. Код не возвращается через публичный API. Новая выдача отличается от непосредственно предыдущей; случайное совпадение обрабатывается ограниченными повторными попытками генерации без записи события отказа.

Случайность внедряется в application как функция без отдельного динамического интерфейса; домен остаётся детерминированным. Событие и outbox по-прежнему записываются атомарно. Убрано лишнее `to_string()` при формировании ответа регистрации. Старые события и snapshots без кода поддерживаются: для неподтверждённой резервации сначала нужно запросить код.

В постоянный набор добавлены проверки реального HTTP → application → CQRS → PostgreSQL пути. Они покрывают 64 конкурентные регистрации одного канонического адреса через два экземпляра приложения, независимые адреса, принудительные гонки reserve/reserve, reissue/verify в обоих порядках, verify/verify и reissue/reissue, откат при отказе outbox, восстановление состояния без проекций и повторную резервацию. После выполнения сценариев проверяются состояние агрегата, последовательности и совпадение payload в events/outbox. Прошли 65 тестов; покрытие строк — 99,23% с исключением только `main.rs`.

Финальные проверки: `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings` и coverage прошли. Полный `cargo test --locked --target-dir /tmp/email-verification-check.xOseIU` также завершился успешно, включая этап doc-tests. В существующем `target` полный запуск выдавал `rustdoc E0463: can't find crate` для зависимостей, хотя все 65 тестов проходили; отдельный запуск doc-tests и полная сборка в чистом каталоге успешны. Настройки проверок не ослаблялись, существующий build-кэш не удалялся.

Первая секция исходного review закрыта **частично**. Канонизация исправлена, подтверждение больше не принимается только по email. Однако короткий код не заменяет постоянный идентификатор поколения: совпадение с более старым историческим кодом не исключено. Защита от устаревшего `ReleaseEmail`, принадлежность резервации пользователю и контракт повторов после неопределённого результата commit остаются отложенными. Семантика `ReleaseEmail` не менялась.

Отправитель outbox, повторы доставки и подтверждения получателя ещё не реализованы: сквозной гарантии at least once нет. Также остаются замечания об ошибках инфраструктуры/replay и необходимость измерений производительности. Для публичного production-сценария верификации ещё нужны срок действия кода, ограничения попыток/повторной выдачи и защита кодов в URL-логах и хранилище.

Ниже сохранён исходный review **до изменений**. Его примеры, числа тестов и ссылки на строки относятся к той версии кода.

## Исходный review

Сейчас я бы не считал систему соответствующей всем пяти требованиям. Атомарная запись и защита от конкурирующих изменений сделаны правильно, но есть воспроизводимый обход уникальности email, проблемы обработки ошибок и существенные пробелы в сценарных тестах. Сквозная доставка пока не реализована.

Изучил весь код сервиса, SQL-схему, тесты и используемые реализации `cqrs-es`/`postgres-es`. Проверки прошли: 42 теста, `fmt`, `clippy`; покрытие строк — 98,95% с исключением `main.rs`. Дополнительные воспроизведения запускал с изолированным PostgreSQL. Исходники проекта не менял.

1. **Строгая консистентность и at least once — требование выполнено частично.**

   Сильная сторона: события и outbox действительно сохраняются одной транзакцией, а успешный ответ возвращается после commit. При искусственном отказе вставки в outbox запись события тоже откатилась. Это правильная граница атомарности: [persist](/workspace/account-management-service/src/infrastructure/postgres/transactional_outbox.rs:146).

   Optimistic locking для одного ключа тоже работает. Принудительно заставил два запроса прочитать одинаковую версию агрегата: один завершился успешно, второй получил `Conflict`; в каждой таблице осталась одна запись. Уникальный индекс PostgreSQL учитывает незавершённые конкурирующие транзакции, поэтому сама по себе загрузка агрегата вне транзакции записи здесь не означает потерю обновлений. [Документация PostgreSQL](https://www.postgresql.org/docs/18/index-unique-checks.html).

   **[P1] Уникальность почтового адреса обходится через отображаемое имя.** Эти три запроса получили `202`:

   ```text
   alice@example.com
   Alice <alice@example.com>
   Bob <alice@example.com>
   ```

   Парсер разрешает такой формат, а ключ агрегата строится из всей строки. Получаются три независимые резервации одного адреса. Нужно либо запрещать отображаемые имена, либо выделять и канонизировать сам адрес. Источники: [парсинг Email](/workspace/account-management-service/src/domain/email_reservation/value_objects.rs:12), [формирование ключа](/workspace/account-management-service/src/infrastructure/cqrs/email_reservation.rs:45).

   **[P1] Повторная резервация не отделена от предыдущей.** Воспроизвёл последовательность: резервирование → освобождение → новое резервирование → старый `VerifyEmail`. Старая команда успешно подтверждает новую резервацию. Команды содержат только email, поэтому определить, к какой попытке относится подтверждение или освобождение, невозможно. Для доставки с повторами нужен идентификатор либо поколение резервации и проверка его соответствия. HTTP-маршруты подтверждения и освобождения пока отсутствуют, но проблема уже существует в [реализованных командах](/workspace/account-management-service/src/domain/email_reservation/commands.rs:5).

   Сквозного **at least once пока нет**: есть надёжное сохранение намерения отправить событие, но нет обработчика outbox, повторных попыток и подтверждения доставки. Это соответствует описанному этапу проекта, однако требование доставки ещё не закрывает. В [main](/workspace/account-management-service/src/main.rs:20) запускается только HTTP-сервис.

   Для завершения нужны понятные инварианты: запись остаётся pending до подтверждения получателя; после сбоя обработка возобновляется; повторная доставка допустима; потребитель корректно переносит дубли. Для идентификации события можно использовать уже существующий `outbox.id`.

2. **Производительность — основа разумная, оптимальность не подтверждена.**

   Tokio с многопоточным runtime, асинхронный SQL и общий пул соединений подходят этой задаче. Глобальной блокировки, последовательно пропускающей все запросы, в коде приложения нет. Добавлять ручное распараллеливание внутрь каждой команды я бы не стал.

   Главный кандидат на оптимизацию — обращения к БД. Для одного события путь содержит чтение истории, `BEGIN`, две последовательные вставки и `COMMIT`. Для пакета выполняется по две вставки на событие. Стоит измерить вариант с `INSERT … RETURNING` и записью outbox через один SQL-запрос, сохранив атомарность: [цикл сохранения](/workspace/account-management-service/src/infrastructure/postgres/transactional_outbox.rs:47).

   Есть и лишние копирования: нормализация создаёт строку, парсер создаёт собственную; application клонирует email; gateway делает строковый ключ; ответ снова вызывает `to_string()`. Последнее особенно просто устранить: `Email` уже реализует `Serialize`, поэтому response может владеть им непосредственно. [Формирование ответа](/workspace/account-management-service/src/presentation/user_accounts/create_user_account.rs:23).

   Дополнительно: каждая команда перечитывает всю историю, поскольку выбран `new_event_store`; размер пула берётся из библиотечного значения по умолчанию; ограничения количества незавершённых HTTP-запросов и явные таймауты SQL не настроены. При росте истории и перегрузке это важнее мелких преобразований типов.

   Без измерений в release-режиме — latency, throughput, аллокаций и ожидания пула — утверждать оптимальную производительность нельзя. Мои конкурентные проверки проверяют корректность, а не скорость.

3. **Абстракции — границы полезные, реализация местами избыточна.**

   Разделение HTTP, бизнес-правил и PostgreSQL оправдано. `Email`, `UserAccountId`, команды и события выражают реальные понятия; удалять их ради сокращения количества типов я бы не рекомендовал.

   Но для одного небольшого use case цепочка `Service → DefaultService → отдельная функция → Gateway → CQRS` тяжеловата. Оба интерфейса действительно используются для подмен в тестах, однако для тестируемости не обязательно сохранять две динамические границы.

   В [application](/workspace/account-management-service/src/application/email_reservation.rs:23) используются два `async_trait`-интерфейса. Каждый соответствующий вызов возвращает упакованный в `Box` future: это реальные аллокации и динамическая диспетчеризация. [Документация async-trait](https://docs.rs/async-trait/0.1.92/async_trait/#explanation).

   Я бы рассмотрел конкретный сервис с одним подменяемым gateway; статическую диспетчеризацию — если измерения оправдают дополнительную сложность сигнатур. Вложенный `Arc<CqrsFramework>` тоже выглядит ненужным при текущем владении.

   При этом количество файлов и делегирующая функция сами по себе не делают программу медленной: здесь нужно разделять сложность чтения и стоимость выполнения.

4. **Лаконичность и ошибки — код читаемый, но семантика ошибок ненадёжна.**

   Доменные обработчики короткие, проверки состояния прямые, преобразования между слоями находятся в понятных местах. Основная проблема — потеря смысла и причины ошибки.

   **[P2] Повреждённые данные выдаются за временную недоступность.** `DeserializationError`, `UnexpectedError` и ошибка соединения превращаются в один `Unavailable`, а исходная причина отбрасывается без журналирования. Проверил: повреждённое сохранённое событие приводит к `Err(Unavailable)`. Повторная попытка такое состояние не исправляет. [Преобразование ошибок](/workspace/account-management-service/src/infrastructure/cqrs/email_reservation.rs:53).

   **[P2; критично для replay] Ошибка чтения потока выглядит как успешное завершение.** Репозиторий делегирует streaming библиотеке `postgres-es`, где чтение выполняется в фоновой задаче с `unwrap()`. На закрытом пуле задача паникует, а вызывающий код получает `None` — обычный конец потока. При восстановлении проекции это может означать незаметно неполный результат. Сейчас этот путь не используется HTTP-командой, но публичный контракт репозитория уже ненадёжен. [Проблемное чтение](/state/home/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/postgres-es-0.5.0/src/event_repository.rs:119).

   **[P2] Инвариант нормализации Email зависит от способа создания.** `Email::parse("Alice@Example.COM")` нормализует адрес, а `Deserialize` сохраняет регистр. Воспроизведение дало два неравных значения. Десериализация должна проходить через ту же проверку и нормализацию: [объявление Email](/workspace/account-management-service/src/domain/email_reservation/value_objects.rs:7).

   Я бы закрепил простые правила: бизнес-отказ не меняет состояние; техническая ошибка сохраняет диагностическую причину; временный сбой отличается от повреждения данных; ошибка связи во время commit допускает неопределённый результат операции. Последний случай требует понятного контракта повторного запроса.

5. **Тестирование — хорошее покрытие локальной логики, недостаточное покрытие системы.**

   В домене проверены все 12 сочетаний четырёх состояний и трёх команд. Есть полезные PostgreSQL-тесты атомарности, конфликтов и snapshots. Это содержательные проверки.

   Но существующий тест дубликата выполняет записи последовательно. HTTP проверяется с заглушкой сервиса, gateway — с `MemStore`, PostgreSQL — с техническим `TestAggregate`. Полного сценария через реальные компоненты и конкуренции за один агрегат в наборе нет.

   Дополнительные проверки дали следующие результаты:

   | Сценарий | Результат |
   |---|---|
   | 64 конкурентных запроса одного нормализованного email через два экземпляра приложения в одном процессе | `1 × 202`, `63 × 409`; по одной записи |
   | Два запроса гарантированно прочитали одну версию агрегата | Один успех, один optimistic conflict |
   | 64 разных email одновременно | Все приняты |
   | Ошибка вставки outbox | Обе записи откатились |
   | Один адрес с разными отображаемыми именами | Ошибочно принят трижды |
   | Старое подтверждение после повторного резервирования | Ошибочно принято |
   | Сбой чтения replay | Ошибочно выглядит как конец потока |

   В постоянный набор я бы добавил эти сценарии, гонки `reserve/release/verify`, повторы команд предыдущей резервации, потерю ответа после commit и отмену запроса во время записи. После появления доставки — сбои до отправки, после отправки до отметки публикации, перезапуск и конкуренцию нескольких обработчиков.

   Требование «все возможные сценарии» стоит выразить через инварианты и управляемые точки конкуренции. Одного массового запуска запросов недостаточно: нужны барьеры между чтением и записью, моделирование отказов и проверки допустимых последовательностей состояний.

Порядок исправления я вижу таким: уникальность адреса и принадлежность команд резервации → корректная передача ошибок → завершение доставки и сценарные тесты → измерения и оптимизация SQL/аллокаций. [Диагностические воспроизведения](/tmp/account-case-review-37rteY/src/main.rs) оставил отдельно от проекта.
